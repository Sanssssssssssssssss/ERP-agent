# 字段拒绝后的自我纠错与执行诊断 · 2026-10-03

Agent 能在部分字段拒绝后自行调整，但原始轨迹不能证明全部字段都完成了业务查验。此次补齐 `diagnose_current_run` 丢失的字段发现提示；全量普通测试 **1353通过、4跳过、201个子断言通过**。

## 原始轨迹

检查四题的148份原始请求和会话回执，逐项核对[17个已冻结字段节点](../experiments/agent_regression/bench_recovery_cases.json)。只统计看到拒绝后的新请求；同一响应中预先安排的工具不算纠错。成功读取必须覆盖原记录ID。

| 观察到的行为 | 节点数 | 可确认的边界 |
|---|---:|---|
| 下一请求改了字段，并成功读取原记录 | 7 | 请求已修正；删除字段不能证明所需业务信息已补齐 |
| 下一请求查了现场字段定义 | 1 | 工作中心案例查到 `capacity_ids`，未见后续显式重读原工作中心记录 |
| 未见同一目标的显式字段读取闭环 | 9 | 可能转向其他证据；保留未确认，不计作恢复失败或成功 |

7个成功读取节点：BT2010-07、BT2030-03/04/10、BT2066-12、BT2279-01/04。BT2030-03/04在纠错请求内也查了字段，但读取和字段发现由同一次模型响应提出，不能说读取依据了该次发现结果。

BT2066-10在0008请求拒绝后，于0009主动查询工作中心字段定义。此前已用其真实纠错上下文做一次API验证，并在隔离Odoo上执行返回的只读字段发现，确认 `capacity_ids → mrp.workcenter.capacity`；该关联字段不能当作旧标量容量字段替换。

17个节点均未看到后续新请求再次触发相同模型、相同缺失字段的拒绝。这支持“没有盲目重复”，不证明没有遗漏业务要求。2279唯一的 `diagnose_current_run` 调用在0029返回 `identity_or_scope_unavailable`；运行关联缺失的修复已在上一轮加入宿主适配器，该历史回执仍保留原结果。

## 根因与改动

- **模型决策：**请求了当前模型定义中没有的字段。版本差异和错误命名都有可能，不能统一断言是旧版本字段。
- **工具与runtime：**原生字段守卫正确拒绝。当前直接回包已有公开字段发现工具、原实例、缺失字段与候选提示。
- **Self debug：**汇总此前只保留 `tool_failed / unknown / fresh_read_or_validate`，丢失了具体恢复入口。共享诊断入口现在保留 `unknown_field / query_invalid / discover_live_fields`，给出原实例的 `mcp_odoo_get_model_fields` 参数，并要求查验名称、类型、关联及业务含义。
- **最终核验：**提示明确要求：必要信息仍读不到时保留未知，不能只删字段就认定核验通过。此次没有新增业务字段自动替换或业务核验规则。

诊断只转发经过格式与长度检查的只读恢复参数，最多列出3个缺失字段并保留总数。任意错误正文、恢复说明、候选文本及额外参数均不复制。关联冲突、未结束RPC、动作回执继续保留原优先级；不确定写入仍要求核对，不自动重放。旧回执缺少结构化恢复信息时仍保持通用诊断。

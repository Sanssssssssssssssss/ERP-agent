# 工作台复盘与 Demo 修复清单

日期：2026-09-09。基线：`3ad9a90` / 桌面 0.3.1。

**当前定位：业务执行原型可用，尚未达到客户 Demo 标准。** 销售开票案例的真实执行、审批和核验结果保留；这些结果不能证明普通会话、连续流式交互及首次使用体验完整。

本轮完成问题收集、证据核对和验收结论更正；下面的功能缺陷尚未修复。主代理负责需求、复核与最终验收，Luna 分项实现。P0 表示阻断本次 Demo，不是安全漏洞等级。

## 复盘

1. **需求约定写偏。** 用户要求像 coding agent 一样先对话，再确认业务。历史 `PLAN.md` 却把没有 business_id 的消息定义成固定销售开票提案，界面上的“讨论业务”没有对应模型链路。
2. **验收跟着实现走。** host 测试直接从任意文字取得 proposal；renderer fixture 的 send_message 返回 null。它们测到了调用去重和页面切换，没有证明“你能干什么”能被回答。
3. **真实运行样本过窄。** 冻结业务包含完整指令，首次失败后还经人工纠正。验收检查了运行、回执和展示，没有覆盖从一句普通问话开始的完整客户旅程。
4. **结论和优化顺序错误。** 将相关回归、构建及单例通过外推为 Demo 就绪，随后优先打包和 token 优化。后续先补产品链路，再评估效率；机械检查和测试数量不替代人工使用验收。

## 业务透明度约定

用户当前要求业务内容充分展示。目标、范围、公开执行说明、SOP/检索来源、Odoo 对象与状态、工具参数、写入前后值、回执和核验结果应当可查看并关联到所属业务。长内容用摘要、展开和搜索处理，不能默默丢掉字段。

密钥、认证头和 cookie 继续隐藏。面向用户的计划和进度使用公开说明、工具事件与业务事实；不把模型内部推理文本当作产品进度。完整过程可查看不等于默认向外部发布业务资料。

## 流式链路修复边界

| 段 | 现状 | 最小改动方向 |
| --- | --- | --- |
| Provider SSE → Pi | 已有解析及文本/其他事件类型 | 复用现有流解析，不新增提供商适配层 |
| Pi → runner/worker | message_update 被过滤，其他事件走 JSONL stdout | 转发公开文本增量，关联明确消息身份 |
| worker → host | 消费工具开始/结束、轮次结束和整条消息 | 接入文本及工具进度，保留终态和审批语义 |
| host → Electron → UI | 已有推送型 IPC；UI 有未接通的 delta 分支 | 使用现有 IPC，补作用域、归并、恢复和界面批量刷新 |

原生桌面无需为此再搭一套 HTTP SSE 服务。普通会话复用 Python Pi 模型循环与持久化能力；会话对话和业务执行须有明确归属，业务确认和逐项动作审批继续分开。

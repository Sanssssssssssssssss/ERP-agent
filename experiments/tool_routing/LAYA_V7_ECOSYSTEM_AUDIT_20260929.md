# Laya v7 接入审计

**存在接入层冗余，主要在工具发布、历史回包投射和 worker 生命周期。** 本轮仅审计源码、回放三条业务的 99 个请求；没有付费调用、GPU 推理或运行时代码修改。冻结源码哈希核验一致。

当前链路：World 历史投射 → 构造一次完整 API payload → 提取 Laya 状态 → GPU 能力选择 → 合并 SOP／未决动作／恢复依赖 → 动态工具发布 → 再构造主模型 API 请求。常规能力选择已经交给 Laya，未发现第二套付费模型路由并行执行。

| 优先级 | 已确认的问题 | 实际证据 | 最小调整方向 |
|---|---|---|---|
| P1 | 未决动作冻结上一轮整套能力 | 9 轮补入了 actions 之外的旧能力；E01 第 8 轮 Laya 仅选 actions，宿主又加回异步、跨实例、诊断、知识、迁移 | 保留当前动作、SOP 和恢复所需能力；不把整个旧集合当作动作依赖 |
| P1 | 工具按总目录过滤，动态工具插到前部 | E02 工具集合变动 42 次，多次第一个工具就变化 | 基础工具固定前置、动态工具稳定排序置后；保持实际 dispatcher 与请求同一集合 |
| P1 | 历史回包在审批续跑后仅因键顺序改变 | 10 次回包改写 JSON 语义完全相同；World 日志按 sort_keys 落盘，重新载入后嵌套 freshness 顺序变，投射输出未规范化 | 模型可见投射统一序列化；原始证据与哈希继续保存 |
| P1 | 在早期历史消息中更新当前 freshness | 11 次历史引用的实时 freshness 变化；E02 第 19 轮改写了早期第 5 条消息 | 历史快照固定，当前失效信息放最新状态；执行前继续 fresh read 和账本检查，不能保留虚假的“仍新鲜”标记 |
| P1 | 选择目标与紧凑工具面的目标不一致 | 问题定义允许探索、允许已有基础工具替代时仍选；迁移／知识／附件分别开放 53／48／53 轮，实际调用均为 0 | 明确下一响应新增能力需求；把基础工具、强制依赖、已有动作约束作为已满足条件。需保留原标签并做局部对照，不能据“没用”直接判错 |
| P2 | 审批暂停连带销毁 Laya worker | 三题有 4／15／7 段 worker 执行；runner 每段新建 provider，关闭时结束 Laya 进程，首轮重新加载模型；模块探测也重复 26 次 | 将只读选择器生命周期与业务 worker 解耦，先补启动／就绪耗时观测；身份与状态仍逐请求绑定 |
| P2 | 已确定的能力仍重复交给分类器判断 | SOP 在 91 轮已要求 actions，仍进行完整分类；worker 忽略候选子集进行全 8 题推理后才过滤结果 | 只判断待决能力；先验证子集推理一致性。当前 396 次 GPU forward 不等于 396 次付费模型调用 |
| P3 | 重复构造请求和扫描日志 | Laya 前后各组装一次完整 API payload；每轮扫描 SOP／动态日志，Laya 又遍历历史及 World | 后续复用已有宿主状态／增量游标。缺少耗时证据，暂不优先重写 |

宿主兜底不能整段删除：本次有 **21 轮 actions 未被 Laya 选中，宿主保留后业务仍通过**。SOP 本轮实际只强制 actions；其整场保留机制是潜在设计问题，并非此次大规模辅助能力扩张的主要来源。审批、ACL、前态校验、未知写入保护、回读与 Laya 职责不同，必须保留。

生命周期重复属于原有架构的成本：旧对照有 4／17／7 段 worker，本次为 4／15／7。它值得优化，但不能用来解释本次相对旧版的请求耗时上升；模型加载尚无独立耗时记录。

**离线工具排序实验**：只重排定义，99/99 请求的工具集合、描述、schema 完全不变。发生工具集合变化时，共同工具前缀中位数：E01 5.5→19、E02 2→20、E03 8→18。这是结构检查，不是 GPU KV 或 API 缓存收益实测。

缓存观察：E02 工具集合不变／变化的轮次，输入缓存占比分别为 92.4%／56.2%。系统提示在每题内固定，单个工具 schema 也固定。三题共另有 37 次正常的历史回包投射变化；旧链路已有该机制，不能把全部缓存下降归给 Laya，也不能为了缓存取消有效外置。

**“放最后”的边界**：API 的顶层 `tools` 字段已经在 `messages` 后组装。修改 JSON 键顺序不能保证改变服务端 prompt 模板。可控的是工具数组顺序、集合稳定性和消息字节；官方说明缓存依赖可复用前缀，但 Command Code 网关的具体模板、路由和缓存行为尚未验证。[DeepSeek 缓存说明](https://api-docs.deepseek.com/guides/kv_cache)。当前证据表明前缀复用变差，没有证据称远端 KV 内存溢出。

建议拆开验收：①统一投射序列化＋基础工具前置；②收窄未决动作保留范围；③对齐选择契约；④独立验证选择器跨审批复用。前两项先回放真实请求及审批续跑，确保 schema、动作依赖和业务事实不丢；然后做有限 API 缓存对照。每项保留独立回退点，不同时改历史压缩策略或重训模型。

排除项：主模型当前不再暴露 configure/list 能力选择工具；Mem0 关闭；ERP 系统提示覆盖通用 Pi Coding prompt；session 的 context usage cache 是本地计数缓存，不是远端 KV。Laya 私有状态不直接拼入主模型历史；双份状态消费不能直接当作付费输入重复。
